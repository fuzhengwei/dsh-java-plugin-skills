# 案例储备智能体应用 Prompt

用途：用户没有明确应用诉求时，从这里抽 **3~5 个跨分类案例**（完整话术，非标题）展示给用户；用户选定（或原样粘贴）后，按该话术直接走 SKILL.md 工作、部署。每个 prompt 均运行，无需补充信息（端口、数据、技术栈等按 SKILL处理）。

## 场景深挖（选定案例后、写码做）

一句话 prompt 是需求输入，**开发前必须深挖成设计稿**，禁止拿到 prompt 直接写码：

1. **实体表**：列出核心实体及段（照下方深挖卡片，或按公式推导）。要够渲染真实页面（如商品：名称/价格/分类/标签/库存/封面渐变色）
2. **工具表**：每个"列表+详情"工具，写清每个工具的入参/出参 JSON 结构和 description（何时必须调用）
3. **页面区块**：hero（大标题+主行动按钮+统计数字）→ 列网格 → 详情/表单 → AI 助手面板；管理台型则： + 数据看板 + 表格 + 操作栏
4. **预置数据**：按 prompt 中规模预置，数据要"像真的中文业务文案、合理价格区间、分布在不同分类）
5. **参照标杆**（可 WebFetch 抓 README 验证业务结构）：电商类参照 [mall](https://github.com/macrozheng/mall)（商品/订单/营销/会员四模块）；UI 组件参照 50projects50days；本技能两个案例源码是最直接的完整实现

### 补充分类深挖卡片（P21~P27，与旗舰卡片同权重执行）

**P21 私人音乐歌单馆**

**P22 财经资讯早报台**
- 实体：资讯(标题/分类[宏观/股市/行业/公司]/来源/发布时间/摘要/关联板块)、板块(名称/涨跌幅/代表标的)、订阅源(名称/类型/更新频率)、自选关注(用户/板块或关键词)
- 工具：news_query(分类/时间段/关键词→资讯列表)、news_detail(id→全文+关联板块)、sector_overview(板块名→涨跌幅+关联资讯)、digest_generate(日期→早报摘要，聚合工具)、subscribe_manage(写操作：关注/取消关注)
- 页面：要闻时间轴 → 板块行情条 → 资讯详情(关联板块高亮) → 早报卡片 → AI 资讯助手
- ⚠️ 硬约束：解读「新闻影响的板块」必须基于 news_detail 返回的关联板块字段，禁止脱离预置数据推演行情涨跌

**P23 智能家居中控台**
- 实体：设备(名称/类型[灯/空调/窗帘/摄像头/温湿度传感器]/房间/状态[开关/数值]/功率W)、场景模式(名称/触发动作列表/启用状态)、能耗记录(设备/日期/度数)、异常事件(设备/类型[离线/数值超标]/时间/处理状态)
- 工具：device_list(房间/类型→设备状态)、device_control(写操作：开关/调节，需确认)、scene_activate(写操作：执行场景联动)、energy_analysis(房间/时间段→能耗统计)、anomaly_query(时间段→异常事件)
- 页面：房间分区设备卡(实时开关) → 场景模式胶囊 → 能耗柱状图 → 异常事件流 → AI 家庭管家
- 状态机：设备 开/关/调节中；异常事件 未处理/已处理（预置数据各状态至少 1 条）

**P24 自媒体创作工作台**
- 实体：稿件(标题/选题分类/状态[构思/写作/审核/已发布]/字数/平台)、选题(主题/来源/热度预估/状态)、发布记录(稿件/平台/发布时间)、数据统计(稿件/阅读/点赞/涨粉/完读率)
- 工具：topic_query(状态→选题库)、manuscript_query(状态→稿件看板)、performance_query(稿件/时间段→数据统计)、title_variants(稿件id→基于历史爆款结构的 3 个标题变体)、topic_suggest(写操作：灵感入库，需确认)
- 页面：稿件看板(四列状态列) → 数据看板(阅读/涨粉曲线) → 选题库表格 → AI 创作助手
- AI 能力↔工具：爆款复盘=performance_query 按阅读排序+规律总结；标题变体=title_variants（基于预置稿件的真实标题，不是凭空创作）
- 状态机：稿件 4 状态齐全

**P25 智慧农场管理台**
- 实体：地块大棚(编号/面积/作物/设备)、作物批次(地块/作物/播种日期/阶段[播种/生长/采收]/预期产量)、传感器读数(大棚/温度/湿度/光照/时间/阈值)、农事任务(批次/类型[灌溉/施肥/巡检]/计划日/状态[待执行/已完成/逾期])、销售订单(农产品/数量/金额/状态)
- 工具：plot_query(→地块+当前批次)、sensor_latest(大棚→最新读数+阈值对比)、task_query(状态/日期→农事任务)、task_execute(写操作：执行回写，需确认)、yield_forecast(批次→产量/收益预估)
- 页面：地块网格(作物+阶段徽标) → 传感器实时卡(超阈值标红) → 农事任务表(逾期高亮) → 订单列表 → AI 农技助手
- ⚠️ 硬约束：灌溉/施肥建议必须引用 sensor_latest 的真实读数与阈值对比，禁止无数据支撑的泛泛建议

**P26 碳普惠生活平台**
- 实体：低碳行为(用户/类型[步行/骑行/公交/垃圾分类]/日期/次数/减碳g)、碳积分账本(用户/积分变动/来源)、公益项目(名称/主办方/目标金额/已捐/状态)、排行榜(周期/个人/社区/排名)
- 工具：behavior_log(写操作：打卡，需确认)、carbon_summary(用户/月份→分类减碳统计)、equivalent_convert(减碳量→等效换算，换算系数预置在应用内)、project_list(类型→公益项目+进度)、rank_query(周期→排行榜)
- 页面：今日打卡胶囊 → 减碳分类环图 → 积分流水 → 公益项目卡(进度条) → 排行榜 → AI 低碳助手
- ⚠️ 硬约束：「相当于种几棵树」必须走 equivalent_convert 工具（系数预置），禁止 AI 自己拍脑袋换算

**P27 AI 应用运行监控台**
- 实体：模型服务(名称/版本/状态[健康/降级/故障]/负责人)、调用记录(服务/时间/时延ms/tokens/成本)、告警事件(服务/类型[超时/错误率/成本]/级别/时间/处理状态)、值班记录(日期/值班人/交接事项)
- 工具：service_list(→服务健康总览)、metrics_query(服务/时间段→调用量/时延/成本)、alert_query(级别/状态→告警事件)、cost_breakdown(时间段→分服务成本对比)、daily_report(日期→聚合日报)
- 页面：服务健康总览卡 → 调用量/时延曲线 → 成本柱状图 → 告警事件流 → AI 运维助手
- ⚠️ 硬约束：根因解读必须基于 metrics_query + alert_query 返回数据；预置数据要有 1 个降级/故障服务 + 对应告警，让「定位异常服务」有的放矢
- 状态机：服务 3 状态；告警 未处理/处理中/已恢复


## 使用规则

1. **用户说 help/帮助/能做什么（要全貌）** → 按「帮助菜单」节三段式回复（能力介绍 + 104 案例全分类菜单 + 引导）
2. **用户问"举个例子/有什么推荐的"（要精选）** → 按下面分类轮换抽 3~5 个（跨大分类），原话术展示，并说明"选定任意一个即可一句话完成开发+部署启动运行"
3. **用户粘贴/改写其中一个** → 该 prompt 即为需求输入，直接进入阶段 0（唯一要确认的只有"新开发 or 对接已有应用"）
4. **用户领域不在库中** → 参照同分类句式即时生成一个同结构 prompt（业务实体 + 5 个 AI 工具 + 前端 + AI 助手 + 交付），同样一句话可执行
5. 展示时附上对应"AI 能力亮点"，这个案例做出来是什么样

## 商城/零售

**P1 虚拟数码商城**：`开发一个 PC 端虚拟数码商城，内置 12 件商品和演示用户，支持商品搜索、购物车、下单、模拟支付和订单查询；页面右上角有 AI 购物助手，能理解自然语言推荐商品、查订单、查物流，接入 DSH 插件后启动给我地址。`

AI 亮点：AI 助手可跨"商品/订单/物流"多工具联动回答（对比推荐、订单追踪一句话完成）。

**P2 生鲜团购平台**：`开发一个生鲜社区团购应用，含今日团购商品列表、拼团进度、自提点选择和订单管理，预置 3 个社区自提点数据；AI 助手可以推荐今日特价菜、查询最近的拼团和自提点，插件接入 DSH 运行起来。`

## 金融/信贷

> 这类场景的共同特征：**输入是"拍一张照片"**，AI 的价值在"看懂图 + 给出可执行的解读"。是实现门槛和演示效果都最出彩的一类——也是 AI Agent 相比传统 CRUD 最有辨识度的场景。技术范式见本节末「视觉场景实现规范」，P100/P101 有完整深挖卡片。

**P100 拍照卡路里管家**：`开发一个拍照识别卡路里的饮食管理应用，支持拍照/上传餐盘照片识别菜品并估算热量、每日摄入汇总、运动消耗记录和热量赤字看板，预置 3 天饮食记录和 60 种食物热量库；AI 饮食助手能解读一餐的热量构成、对比每日摄入与目标、给明日饮食调整建议，以插件接入 DSH 运行。⚠️ 免责声明：热量为估算值，仅供参考。`

AI 亮点：「这顿饭多少卡」→ 拍照识别 → 热量库 × 分量估算 → 计入当日赤字看板，一图一答闭环。

**P101 住宅风水趣味点评台**：`开发一个住宅户型风水点评应用，支持上传户型图/房间照片、方位朝向标注、格局解读报告（动线/采光/功能分区/传统民俗观点）和改善建议清单，预置 6 套户型样张和 30 条民俗格局规则库；AI 风水顾问能按户型图逐区点评、把民俗说法翻译成现代居住学语言（通风/采光/动线）、给低成本改善方案，以插件接入 DSH 运行。⚠️ 免责声明：传统民俗观点，仅供娱乐参考。`

AI 亮点：「这个户型怎么样」→ 上传户型图 → 逐区结构化分析 → 民俗规则库条目化点评 → 给出可执行的改善清单，而不是玄学话术。

**P102 拍照识花·绿植管家**：`开发一个植物识别与养护应用，支持拍照识别植物品种、养护档案（浇水/光照/施肥周期）、黄叶等问题诊断和植物社区笔记，预置 20 种常见绿植的养护周期表；AI 绿植助手能识别品种并给养护卡、按黄叶照片诊断问题原因、生成一周养护日程提醒，以插件接入 DSH 运行。`

**P103 小票拍照记账台**：`开发一个拍照记账应用，支持拍购物小票/外卖单自动识别品项与金额并归类记账、月度分类统计、预算超支提醒，预置 10 张样张小票和一个月账单；AI 记账助手能核对小票识别结果与手改差异、按消费结构给省钱建议、对可疑重复记账给合并提示，以插件接入 DSH 运行。`

**P104 车损拍照定损估价台**：`开发一个车辆损伤拍照估价应用，支持拍车辆损伤部位照片、识别损伤类型与程度、按预置配件价目与工时费估维修区间、生成送修比价单，预置 5 个损伤案例样张和 40 项配件价目；AI 定损助手能解读损伤照片、给出维修方案与价格区间、对比 3 家维修厂报价生成比价建议，以插件接入 DSH 运行。⚠️ 免责声明：估价仅供参考，以线下定损为准。`

### 视觉场景实现规范（图像输入硬规则，设计稿阶段逐条核对）

1. **图像链路固定范式**：前端拍照/上传 → 应用存储并生成 `image_id`（内存 Map，含文件名/大小/上传时间元数据）→ AI 工具以 `image_id` 为入参（**工具 schema 禁止 base64/文件流**，DSH 工具参数走 JSON）→ 应用内识别服务返回**结构化 JSON**（如 `{items:[{name,portion,confidence}],totalKcal}`）→ AI 基于结构化结果解读
2. **识别实现两路径（设计稿二选一并写明）**：
   - **路径 A（默认，零依赖）**：预置样张库——应用内置 8~12 张样张（内联 SVG 插画模拟照片，禁止外链图片保证离线可跑），每张带人工标注的识别结果；用户点「试一试样张」直接走识别闭环，上传真图时降级为 AI 引导式问答（结合预置知识库估算并明示"基于你的描述估算"）
   - **路径 B（增强）**：应用侧配置视觉模型 API（OpenAI 兼容 vision 接口），上传即识别；需用户配 key，交付时说明该前提
3. **数值必须有据**：卡路里/估价/养护周期等数值 = 工具返回的预置库数据 × 识别分量，换算系数预置在应用内，禁止 AI 现编；识别结果必须带 `confidence` 置信度字段
4. **免责声明强制**：视觉估算类页面固定位置展示免责声明（卡路里"估算仅供参考"、风水"传统民俗观点仅供娱乐"、定损"以线下定损为准"），系统提示词同步划界（AI 只解读结构化结果，不做医疗/法律结论）
5. **验收加项**：样张识别结果与人工标注一致；上传交互真实可用（拖拽/选择文件）；识别中有扫描动画反馈

### P100 拍照卡路里管家深挖卡片

- 实体：食物(名称/每100g热量kcal/类别[主食/蛋白/蔬果/饮品/零食])、餐次记录(用户/日期/餐次[早/午/晚/加餐]/菜品明细[食物×分量g]/总热量)、运动消耗(类型/时长/消耗kcal)、用户目标(每日摄入目标/减重速率)
- 工具：`analyze_meal_photo`(image_id→识别菜品+分量+热量+置信度，走路径 A 样张库)、`food_kcal_query`(食物名→热量库)、`daily_intake`(日期→三餐汇总+赤字)、`exercise_log`(写操作：记录运动，需确认)、`diet_suggest`(目标+近3日数据→调整建议)
- 页面：今日热量环图 hero → 拍照识别卡（扫描动效→结果卡带置信度）→ 三餐时间线 → 热量赤字 7 日趋势 → AI 饮食助手
- ⚠️ 硬约束：识别返回的每个菜品必须能在热量库找到对应条目；「这顿多少卡」必须走 analyze_meal_photo，禁止按图猜

### P101 住宅风水趣味点评台深挖卡片

- 实体：户型(名称/面积/朝向/房间列表[类型+位置+门窗])、样张图(户型 SVG 标注图/关联户型)、民俗规则(条目[如"开门见灶"]/现代居住学解读/严重度[提示/建议/注意])、点评报告(户型/逐区结论/改善清单/日期)
- 工具：`analyze_layout`(image_id→户型结构化解析[房间/方位/动线])、`fengshui_rules_query`(格局特征→匹配规则条目+现代解读)、`layout_report`(户型id→完整点评报告)、`improve_plan`(写操作：生成改善清单，需确认)、`case_compare`(→库内相似户型对比)
- 页面：户型上传卡（标注式预览）→ 逐区点评卡（方位罗盘视觉母题）→ 规则命中列表（严重度徽标）→ 改善清单（低成本/中成本分组）→ AI 风水顾问
- ⚠️ 硬约束：每条点评必须关联规则库条目编号并附现代居住学翻译（"穿堂煞"→"南北通透但缺玄关，隐私与保温弱"）；娱乐定位，禁止吉凶断言式话术

## Prompt 结构公式（用于生成库外案例）

```
开发一个 PC 端 <领域应用>，
含 <核心功能 3~4 项>，预置 <演示数据规模>；
AI <角色名>助手能 <3 个跨工具的智能能力>，
<以插件接入 DSH 运行 / 启动运行给我地址>。
```

生成时保持：**业务实体明确**（便于列实体→设计工具）、**AI 能力必须跨工具联动**（体现智能体价值，而非单查询）、**演示数据有规模**（页面不空）。

**硬规则（防 AI 现编，设计稿阶段逐条核对）：**
1. prompt 中每一个 AI 能力，必须能指出支撑它的具体工具（如「解读板块影响」→ news_detail 关联板块字段）；指不出来的，要么补工具、要么改能力描述，禁止让 AI 脱离预置数据推理
2. 凡是「控制/执行/打卡/下单」类真实场景，必须设计写操作工具 + ≥3 状态的状态机，且预置数据覆盖每个状态（没有写操作的业务系统看起来像假的）
3. 涉及数字换算（减碳等效、汇率、费用估算、卡路里）的，换算系数必须预置在应用内并走工具，禁止 AI 现算

每个案例默认交付：DSH 8090 + 应用地址 + 插件工具清单 + 使用说明。

## 细腻度规范（防"路线A/路线B"式敷衍，生成后逐条验收）

一句话 prompt 定不了细腻度，细腻度靠**数据样本标尺 + 验收清单**保证。写预置数据前先读这节；生成的应用对照清单逐条自检，任何一条不过就重做数据，不交"占位符产品"。

### 一、数据样本标尺（照这个密度写，各领域举一反三）

**差（禁止）** vs **好（必须）** 对照：

```text
✗ 路线A：名称"自然科考路线"，价格 3000，3 天
✓ 云南高黎贡生物科考营：名"遇见滇金丝猴·高黎贡生物科考 5 日营"，
  适合年龄 9-14 岁，¥5,980/人，7 月 12 日/7 月 26 日两期各剩 6/11 位，
  亮点"红外相机布设实操 + 长臂猿鸣声记录 + 中科院研究员随营"，
  D1 抵达保山·营地安全 D2 滇金丝猴栖息地监测 → D3 夜行性动物观察…

✗ 商品A：名称"手机"，价格 999
✓ 「星尘 X7 Pro」5G 旗舰，12GB+512GB 深空灰，¥4,299，
  库存 37，标签"旗舰芯 影像旗舰 / 12 期免息"，
  卖点文案"2 亿像素主摄，暗光成片率提升 40%"

✗ 医生A：内科张医生
✓ 林晚晴 · 心血管内科 · 主任医师 · 从业 18 年，
  简介"擅长高血压、冠心病个体化诊疗与心脏康复管理"，
  本周三/五上午门诊，余号 3/7 个

✗ 工单A：标题"系统报错"
✓ 【P1】"核心支付回调超时率 3.2%，影响微信渠道订单"，
  提交人 王倩，指派 陈立（支付组），已处理 2h，
  时间线：16:02 告警触发 → 16:10 定位网关超时 → 16:45 降级预案生效
```

**名称有品牌/地名/编号、价格符合真实区间、数量有余有缺（别全是整数）、日期具体到日、文案有行业术语和数字**。中文数据一律写真实业务感中文，禁止 lorem ipsum、"测试数据"、"示例"字样出现在页面上。

### 二、文案样本（hero、空态、按钮、AI 气泡）

- Hero：`这个暑假，把孩子交给大自然` ＋ 副标 `中科院研究员随营的 12 条科考路线，正在报名`（不是"欢迎来到研学平台"）
- 空态：`7 月的营位已经报满啦，8 月路线即将看看往期路线过过瘾` ＋ 按钮「看往期路线」（不是空白或"暂无数据"）
- 按钮：动词开头带场景——「选这个排期」「加入购物车」「发起拼团」（不是「确定」「提交」「OK」）
- AI 气泡开场：`你好呀～想给孩子找哪个方向的营地？科考、人文还是编程？告诉我年龄和兴趣，我帮你挑几条 👇`（不是"您好，请问有什么可以帮您？"）

### 三、细腻度验收清单（生成完逐条过，任一不过 = 不合格重做）

1. **数据密度**：每条核心数据 ≥ 6 个有意义字段；列表页首屏能看出"这是个真产品"
2. **数据间有故事**：数据互相咬合——有满员的排期也有剩 2 位的排期；有已完成订单也有配送中的订单；用户 A 的点评引用了商品 B。禁止所有记录同质化
3. **文案零占位**：全站搜索不到"示例/测试/XXX/xxx/Route A/商品A"
4. **数字有算术合理性**：订单金额=商品价格×数量；拼团进度=已拼/总人数；统计数字与明细加总一致
5. **状态机完整**：核心实体有 ≥3 种状态且都能在预置数据中看到（待支付/已支付/已完成/已退款各至少 1 条）
6. **AI 回答有据**：让 AI 助手查任何一个工具，返回的数据在页面上能找到对应（工具查的就是预置数据，不是现编）；prompt 中的每个 AI 能力都能对应到具体工具（见「硬规则」）
7. **移动端不塌**：缩到 375px 宽无横向滚动、卡片单列、导航可用

### 四、库外案例同样执行

用 Prompt 结构公式生成库外案例时，交付前必须按本节清单验收；案例 prompt 本身不写数据细节没关系，**细腻度由本规范兜底**，不依赖用户把 prompt 写得多细。
